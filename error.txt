Errors and mistakes hit while porting Ember to iPhone (ember-ios).
Newest last. Format: Problem / Location / Action / Cause / Fix.

---

Problem: python could not open a file that had just been written to /tmp.
Location: shell, writing a scratch copy of src-tauri/src/lib.rs
Action: splitting lib.rs into a head and a tail before rewriting it
Cause: this is Git Bash on Windows. "/tmp" in a bash redirect and "/tmp" as
       seen by native Windows python are two different places.
Fix: use the session scratchpad directory with a full Windows path
     (C:/Users/.../Temp/claude/.../scratchpad) for every intermediate file.

---

Problem: bash reported "unexpected EOF while looking for matching quote" on a
         heredoc that looked balanced.
Location: shell, writing the new src-tauri/src/lib.rs
Action: cat > file <<'RUST' ... RUST with a long Rust body
Cause: two stray non-ASCII characters had ended up inside a comment in the
       body, and the shell mangled the encoding.
Fix: write files longer than a few lines with the Write tool rather than a
     heredoc. Keep source comments ASCII.

---

Problem: backup_save_copy would have deleted the snapshot it was about to
         move, so every backup copy would have failed with "There was no copy
         to save."
Location: src-tauri/src/ios_extras.rs
Action: writing the iOS replacement for Backups.saveCopy() in Backup.kt
Cause: backup_save_copy called backup_snapshot_path to find the file, but that
       command's job is to hand SQLite an EMPTY path, so it removes whatever is
       there first. Two different jobs behind one name.
Fix: split them: snapshot_file() computes the path, backup_snapshot_path()
     computes it and clears it, backup_save_copy() only computes it.

---

Problem: a reply typed into a day reminder would have been saved twice - once
         by the webview and once by the Swift handler.
Location: ios/App/EmberNotificationHandler.swift, src/dayReminders.ts
Action: adding a native handler so replies still work when Ember is closed
Cause: tauri-plugin-notification installs its own UNUserNotificationCenter
       delegate to deliver actions to JavaScript. Setting a second delegate
       either replaces it (breaking onAction) or duplicates the work.
Fix: EmberNotificationHandler.install() keeps a reference to the plugin's
     delegate and forwards every callback to it. It only writes to the inbox
     when UIApplication.shared.applicationState != .active - i.e. when there
     is no webview to handle it.

Problem: one test failed after removing the "pc" (paired computer) provider.
Location: src/ai/smallModels.test.ts:19
Action: npx vitest run
Cause: the test asserted that provider "pc" gets compact context mode. That
       provider no longer exists in this edition, so it falls through to the
       big-model default.
Fix: dropped that assertion and renamed the test. The remaining providers
     (local, cloud) are still checked.

Problem: two "declared but never read" type errors after removing the computer

Location: src/ai/reviewJobs.ts:6, src/windows/Settings.tsx:25
Action: npm run typecheck
Cause: getSetting and getProvider were only used by the code paths that

Problem: the widget didn't compile: "'containerBackground(_:for:)' is only
         available in iOS 17.0 or newer".
Location: ios/EmberWidget/EmberWidget.swift:61
Action: first CI run on a macOS runner (GitHub Actions)
Cause: the widget was written against iOS 16, but from iOS 17 a widget must
       declare its own background, and containerBackground - the only way to
       do that - doesn't exist before 17.
Fix: EmberWidget's deployment target is iOS 17.0 (the app stays at 16), and
     the three structs carry @available(iOS 17.0, *). The CI Swift typecheck
     now uses each target's real minimum version instead of 16 for all three.

---

Problem: xcodebuild reported BUILD FAILED with no "error:" line anywhere, and
         the build had quietly used the debug configuration.
Location: .github/workflows/ios.yml, the xcodebuild step
Action: second CI run
Cause: cargo-mobile2 names the build configurations in lower case - "release",
       not "Release". Asking xcodebuild for a configuration a project doesn't
       have is not an error: it builds debug instead. Tauri's debug build
       script then looks for the `tauri ios dev` server and panics.
Fix: read the scheme and the release configuration out of
     `xcodebuild -list -json` rather than guessing them.

Problem: reading the configurations from that JSON threw KeyError:
         'buildConfigurations'.
Location: .github/workflows/ios.yml
Action: third CI run
Cause: `xcodebuild -list -json` doesn't use that key name.
Fix: look for whichever key holds a non-empty list and has "config" in its
     name, and fall back to "release".

Problem: even building the real "release" configuration, the Rust build phase
         panicked: "failed to read missing addr file
         /var/folders/.../dev.abhij.ember.ios-server-addr".
Location: .github/workflows/ios.yml, and Tauri's generated Xcode project
Action: fourth CI run
Cause: the generated project's "Build Rust Code" phase calls back into
       `tauri ios xcode-script`, which reads options the Tauri CLI writes to a
       temp file before it starts xcodebuild. Running xcodebuild directly
       skips that, so the file never exists. No configuration fixes this - a
       bare xcodebuild simply cannot build a Tauri iOS project.
Fix: build through `npx tauri ios build` instead. The target is the simulator
     (--target aarch64-sim), because a simulator build is never code-signed
     and so needs no Apple account. The Rust for a real iPhone is compiled
     separately in an earlier step.

Problem: BUILDING-ON-A-MAC.md told the reader to add two calls to the
         AppDelegate, and two Swift files existed only to be called from there.
         There is no AppDelegate.
Location: BUILDING-ON-A-MAC.md, ios/App/EmberLaunch.swift,
          ios/App/EmberNotificationHandler.swift
Action: reading cargo-mobile2's iOS templates to automate the Xcode work
Cause: `tauri ios init` generates one entry point, Sources/<app>/main.mm, and
       all it contains is `ffi::start_app()`. Tauri builds the UIApplication
       and its delegate inside Rust. There is no
       application(_:didFinishLaunchingWithOptions:) to edit, and no
       application(_:open:options:) either. The instructions described a file
       that does not exist.
Fix: three separate changes.
     - The App Group path now reaches Rust from ios/App/EmberBootstrap.mm,
       whose +load the Objective-C runtime calls before main().
     - The URL scheme is gone. The widget, the Control Centre button and the
       Shortcuts action all run an App Intent, and an App Intent runs code
       before the app opens - so it writes its own inbox line. That removed
       CFBundleURLTypes and any need for a deep-link plugin as well.
     - EmberNotificationHandler.swift moved to trash/ios-no-appdelegate/ with
       a note: it cannot be installed from anywhere, and two handlers for one
       reply would save the same note twice.

Problem: Phase B asked someone to create two targets by hand in Xcode, which
         was the least verifiable part of the whole port.
Location: BUILDING-ON-A-MAC.md
Action: same investigation
Cause: assumed `tauri ios init` writes an .xcodeproj. It doesn't - it writes
       an XcodeGen spec, src-tauri/gen/apple/project.yml, and generates the
       project from that.
Fix: scripts/xcode-extensions.py patches that YAML: both app-extension
     targets, the App Group entitlement on each, the app's own extra sources,
     and the embedding. CI runs it and fails if either .appex is missing from
     Ember.app/PlugIns.

Problem: `xcrun simctl get_app_container <udid> <id> group.dev.abhij.ember.ios`
         printed its usage text and exited 117, failing the build.
Location: .github/workflows/ios.yml
Action: testing that a note left in the App Group folder reaches the journal
Cause: not a bug in the port. An App Group is granted by a provisioning
       profile, and an unsigned simulator build has none, so the simulator
       never creates a container for it. Ember's fallback - its own folder -
       is what every earlier test actually exercised, which is why they passed.
Fix: the step now looks first, reports "NOT PROVEN" with the reason, and
     exits 0. It runs the real test only when a container exists, which will
     be on a device with a profile that grants the group. Written down in
     WHAT-IS-UNVERIFIED.md and first on the by-hand checklist rather than
     quietly assumed.
